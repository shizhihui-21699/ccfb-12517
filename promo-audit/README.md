# 优惠叠加漏洞排查工具 (promo-audit)

读入商城全部优惠规则与互斥配置,自动穷举**商品组合 × 券使用顺序 × 拆单方式**,
找出四类问题并给出可复现的下单步骤:

| 类型 | 说明 |
|---|---|
| `non_positive` | 最终实付 ≤ 0(叠穿) |
| `below_cost` | 实付低于商品成本价 |
| `exclusion_bypass` | 通过拆单等方式绕过互斥限制,互斥的券同时生效 |
| `split_arbitrage` | 拆单合计比单订单最优价更便宜(如满减被多次触发) |

## 快速开始

```bash
# 独立运行(不需要 Laravel,PHP >= 8.1)
php bin/audit                          # 用自带样例规则跑
php bin/audit --rules=rules.json       # 用自己的规则
php bin/audit --json=report.json       # 输出 JSON 报告(含逐步骤明细)
php bin/audit --no-split               # 只审单订单
```

有发现时退出码为 1,可直接挂 CI。

## Laravel 集成

1. 把 `src/` 作为包引入(或拷入 `app/Services/PromoAudit`);
2. 注册 `laravel/PromoAuditServiceProvider.php`,`php artisan vendor:publish --tag=promo-audit-config`;
3. 在 `config/promo_audit.php` 配置规则,或改 `PromoAuditCommand` 里的注释示例从 DB 加载;
4. `php artisan promo:audit --json=storage/app/promo_audit.json`。

## 规则模型(为什么这些配置是漏洞高发区)

- **满减 / 折扣券的门槛基数** `threshold_base`:
  - `original`:门槛看**优惠前**商品金额。多张券叠减后应付已远低于门槛,系统仍按原金额
    判定「满足门槛」继续减 —— 这是叠穿到负数的最常见原因;
  - `current`:门槛看当前应付,安全得多。
- **品类券在部分减免后的基数**:本工具按「范围内金额占比 × 当前应付」比例分摊,
  与多数电商实现一致。
- **积分抵现**:按当前应付的百分比封顶;积分池在拆单间共享(工具按单订单独占估算,是下界)。
- **互斥只在单订单内校验**:拆成两单,每单各用一张互斥券,服务端若不做跨订单校验即被绕过。
- **满减按订单触发**:拆单后同一满减规则可在每个子订单各触发一次。

引擎有两个开关用来复现线上缺陷模式:`clamp_at_zero`(是否把应付截断到 0)、
`enforce_exclusions`(服务端是否校验互斥)。排查时保持 `clamp_at_zero=false`
才能看到「如果不截断会叠到多少」。

## 搜索与剪枝设计

搜索空间四层,逐层压缩:

```
购物车组合 × 会员等级 × 券使用序列 × 拆单方案
```

1. **购物车层(组合剪枝)**
   限制 SKU 种类数、单 SKU 数量、总件数(`search.max_*`)。漏洞复现只需要
   最小购物车,大件数组合是冗余的 —— 同签名发现只保留件数最少、实付最低的。

2. **券序列层(排列 → DP)**
   n 张券的排列有 n! 种,但「最终应付」只取决于(当前应付, 已用券集合)。
   用 DFS + 记忆化把排列枚举压成 `O(不同应付值 × 2^n)`;同类型可交换的券
   天然合并到同一状态。互斥对在展开时直接剪枝,不进入求值。

3. **单调性剪枝**
   - 积分抵现对最终价单调递减:只取「用满 / 不用」两档,不枚举积分数额;
   - 减免全部 ≥ 0,应付沿序列单调下降,DP 状态构成 DAG,无环可 memo;
   - 发现按签名去重,已找到 ≤0 的最小复现后,更大的同规则组合不再报告。

4. **拆单层(不枚举订单对,改为查表)**
   先缓存每个购物车的单订单最优价 `best(cart, 等级, 券子集, 有无积分)`;
   拆单时只做购物车内划分(每行:给 A / 给 B / 按数量拆,Π(qty+1) 种)
   × 券预算分配(每张券:给 A / 给 B / 不用,3^k 种)× 积分归属(2 种),
   全部查表求和,不重新求价。划分出的子购物车必然也在枚举空间内,缓存必命中。

**判定逻辑**:拆单合计 < 同购物车单订单最优价 → 存在套利;
若两单实际生效的规则中存在互斥对 → 升级为「绕过互斥限制」。

## 样例数据能复现什么

`data/sample_rules.json` 按常见电商玩法编了 8 个商品、7 条规则、2 对互斥,
一次运行(约 2 秒)能找到:

- 饮品满30减20 + 新人券满20减12 同品类未配互斥 → 叠到 **-17 元**;
- 服饰 7 折券 + 满减 + 积分 → 长裤实付 45 元(成本 70);
- 8 折券与 7 折券互斥,但拆成两单各用一张 → **绕过互斥**,比单订单再省 10~23 元;
- 全场满100减25 按订单触发 → 两条长裤拆两单,**满减触发两次**。

## 已知边界(诚实清单)

- 拆单只枚举「拆 2 单」;拆 3 单以上通常边际收益递减,且会显著放大搜索空间;
- 积分池在拆单间按单订单独占估算,是**下界**(实际可用积分更少,真实实付只会更高,
  所以报出来的都是保守可复现的);
- 品类券的部分减免基数采用比例分摊模型,若你的系统是「按行分摊到商品」,
  需在 `RuleContext::scopeShareOfPayable` 处替换实现后再审;
- 运费、限时秒杀、拼团等玩法未建模,可按 `PromotionRule` 接口扩展。
